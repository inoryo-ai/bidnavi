## 0. この改訂について

### 0.1 なぜ書き直したか

v2.0 は「これから作るもの」の想定で書かれていた。
技術検証（開発ループ5周・211テスト）で実際に作って測った結果、
**v2.0 の中核的な前提が2つ、実測で否定された**。

想定のまま Phase 1 に進むと、コスト設計とマッチング設計の両方が破綻する。
よって要件定義から書き直す。

### 0.2 名称について（2026-09-07 調査で確定）

当初この企画に付けていた仮称は**使わない**。同名の先行サービスが実在するため。

- 株式会社ヴィジュアライズが「**BID navi**」を提供していることを、ASCII.jp の
  ローンチ記事で確認した（全国の自治体・省庁の入札／プロポーザル情報をAIで
  一括自動収集し、無料で検索できるサービス）。
- ⚠️ ただし記事に記載のドメインは**現在DNS上に存在しない**（サービス終了または移転の可能性）。
  「現在も運営中か」は未確認。**存続の有無に関わらず、紛らわしい名称は採らない**。

→ **W0-1 の商標調査を通過するまで製品名を付けない。**
   リポジトリ・パッケージは製品名ではなく説明的な名前（`tender_pipeline`）を使う。
   ブランド名を先に決めると、あとで全資産の作り直しになる。

### 0.2a v2.0 から撤回した前提（重要）

| # | v2.0 の前提 | 実測結果 | v3.0 の扱い |
|---|------------|---------|-----------|
| A | 調達ポータル（GEPS）のオープンデータを A枠の収集対象にする | **`/robots.txt` すら OAuth にリダイレクト＝認証必須**。スクレイピング対象にならない | **撤回**。対象から除外（§4.4） |
| B | 2段目に埋め込みベクトルを入れれば、案件名だけで安価に足切りできる（通過率 5%→1%） | **否定**。`multilingual-e5-small` は文字バイグラムと同等かわずかに劣る。Recall 100% には評価30件中**22件（73%）**を3段目に回す必要があった | **撤回**。§9 でコスト制御の設計を作り直した |

### 0.3 前提Bの実測データ（撤回の根拠）

対象プロフィール「業務システム開発会社」に対する、案件名の類似度。

| 案件名 | 正解 | 文字バイグラム | 埋め込み(e5-small) |
|--------|------|--------------|------------------|
| 基幹業務システム改修業務委託 | ◯関係あり | 0.586 | 0.849 |
| ネットワーク機器保守業務 | ◯関係あり | 0.120 | 0.845 |
| 庁内LAN更改に伴う設定業務 | ◯関係あり | 0.105 | **0.856** |
| 統合型GIS運用支援業務 | ◯関係あり | 0.114 | 0.843 |
| RPA導入支援業務委託 | ◯関係あり | 0.120 | 0.840 |
| 庁舎警備業務委託 | ×無関係 | 0.143 | **0.855** |
| 市道○○線舗装補修工事 | ×無関係 | 0.000 | 0.821 |

- 埋め込みは「関係あり」を軒並み拾い上げるが、**「庁内LAN更改（関係あり・0.856）」と「庁舎警備（無関係・0.855）」が区別できない**。
- 関係あり群と無関係群の**分離幅は -0.001**（＝分布が重なっている）。絶対値の閾値が引けない。
- 中心化（異方性補正）も試したが、`市道○○線舗装補修工事` が3位に上がって悪化した。
- 評価セット30件での Recall@K も、埋め込みとバイグラムでほぼ同じ（K=15 で 73.3% vs 80.0%）。

> **⚠️ この実測の限界（正直に）**
> ①評価セットは合成30件で、実案件ではない ②試したのは `e5-small` のみで、
> `ruri-base` や `e5-large` は未検証 ③比較対象（業種ラベル／過去実績案件名）の両方で
> 試したが、いずれも分離できなかった。
> **「埋め込みは絶対に使えない」ではなく「使えるという前提で設計してはいけない」が結論。**
> §15 の W0 で、実案件と上位モデルで再検証する。

### 0.4 技術検証で確定した事実（v3.0 の土台）

実装して動かした結果、**設計判断として確定**したもの。これらは v3.0 の要件に組み込む。

| # | 確定事項 | 根拠 |
|---|---------|------|
| 1 | 「取得成功(N件)」と「取得成功(0件)」を別ステータスにすれば、サイレント故障は検知できる | 障害注入テストで、構造変化→例外→failed→アラートが一本で通ることを確認 |
| 2 | **件数監視では検知できない故障が実在する** | 実サイトで2件発見（§0.5） |
| 3 | 時刻不明の締切は、通知と締切判定で**逆向き**に倒す必要がある | 統一すると必ずどちらかで案件を失う |
| 4 | 案件名の正規化だけでは名寄せは足りない。空タイトルは例外にする必要がある | `令和8年度` だけのタイトルが空文字化し、全案件が1件に潰れる事故を発見 |
| 5 | 金額の単位（千円・百万円）を取りこぼすと桁が3つずれる | `1,234千円` → 1,234円 のバグを発見 |
| 6 | キーワードは「必ず通知する保証」であって「フィルタ」ではない | キーワード未設定の利用者に通知が0件になる事故を発見 |
| 7 | Python + `pdfplumber`/`bs4`/`playwright` が妥当なスタック | 全て導入済み・実サイトで動作確認済み |

### 0.5 件数監視で検知できない故障（新しい要件を生んだ発見）

実サイトで見つかった、**例外が出ず・件数も正常なのにデータが壊れている**2つの故障。
FR-105 の件数監視では原理的に検知できないため、v3.0 で新たに §7.4「データ健全性検査」を設けた。

| # | 故障 | なぜ検知できないか | 結果 |
|---|------|-----------------|------|
| D-1 | 横浜市が `Content-Type` に charset を返さず、`requests` が ISO-8859-1 と誤認して**案件名が文字化け** | HTTP 200・件数5件・例外なし | natural_key が毎回変わり名寄せ破綻／`【契約結果公表】`判定が効かず**終了案件を募集中として通知** |
| D-2 | 日本語PDFのフォントに ToUnicode マップが無く、抽出結果が `(cid:1234)` の羅列 | 抽出「成功」・文字数も十分 | 意味不明な文字列をLLMに投げ「関係なし」と判定され取りこぼす |

## 1. 背景と課題

### 1.1 市場構造

日本の公共調達は、国・都道府県・市区町村・独立行政法人など**数千の調達機関がそれぞれ独立して公告を出す**。
全国横断の公式な一元窓口は存在しない。

- 地方自治体は「電子入札コアシステム」系や独自の入札情報公開システムを個別運用しており、
  URL構造・HTML構造・公開形式（HTML/PDF/Excel）がバラバラ。
- 国のGEPS（政府電子調達システム）は**認証必須**であり、機械的な収集の対象にならない（§0.2-A）。

### 1.2 顧客の課題

| # | 課題 | 本システムが解く度合い |
|---|------|----------------------|
| C-1 | 情報が分散していて「探す」コストが大きい | ◎ 中核 |
| C-2 | 公告から締切まで短い（法令上「10日前まで」の公告で足りる）。3日遅れると実質応札できない | ◎ 中核（速報性） |
| C-3 | 「良い提案をした会社」ではなく「情報収集に人を割ける会社」が勝つ構造 | ◎ 中核 |
| C-4 | 落札者・落札額・入札者数の履歴がないと「勝てるか」が判断できない | ○ Phase 3 |
| C-5 | 案件名だけでは自社に関係あるか分からず、仕様書PDFを開かないと判断できない | ◎ 中核（§0.3 で難しさが確定） |

> **C-2 の法令根拠**：一般競争入札の公告期間は、国は予算決算及び会計令、地方は地方自治法施行令に
> 「入札期日の前日から起算して少なくとも10日前」（急を要する場合は短縮可）と定められている。
> **10日は「最短」であって例外ではない。**
> ※ WTO政府調達協定の対象となる大型案件は公告期間が長く（40日級）、切迫度は下がる。
> **本システムの主戦場は協定対象外の中小規模案件。**

> **C-5 について（v3.0 の重要な認識）**
> §0.3 の実測は、C-5 が「AIで簡単に解ける」課題ではないことを示している。
> 案件名だけでは、人間でも機械でも判定できない。だからこそ顧客はPDFを開いている。
> **この課題は「安く」は解けない。仕様書を読む処理に相応のコストがかかることを、
> 事業計画の前提に組み込む必要がある（§9・§16）。**

## 2. 目的と成功基準

### 2.1 プロダクトの目的

> **中小事業者が、自社に関係のある入札案件を「探さずに」受け取り、
> 応札するかどうかを当日中に判断できる状態をつくる。**

### 2.2 指標の優先順位（設計思想）

**Recall（取りこぼさない）を Precision より優先する。**
1件の見逃しが顧客の受注機会喪失に直結するため、多少の誤検知は許容する。

- **F1 を主指標にしてはならない。** F1 は両者を対等に扱うので、
  「取りこぼしを増やして誤検知を減らす」改善を良い変更として評価してしまう。
- ただし Precision を無視すると通知疲れで解約される（指摘#10）。
  Precision は「下限を守る制約」として扱い、最適化はしない。

### 2.3 KPI

| 区分 | 指標 | 目標 | 測定方法 |
|------|------|------|---------|
| **KPI-1** | **取りこぼし率（FNR）** | **≤ 3%** | 評価セット（§10）に対する実測 |
| **KPI-1b** | **構造的取りこぼし率** | **0%** | 関係ある案件のうち、判断の機会（ルール一致 or LLM到達）を得られなかった割合。**AIをどれだけ良くしても拾えない分**。実装済み |
| KPI-2 | 適合率（下限制約） | ≥ 70% | 同上 |
| KPI-3 | 速報性（公告掲載→通知の中央値） | ≤ 60分 | 公告日時とpush時刻の差分ログ |
| KPI-4 | 収集成功率 | ≥ 99% | `crawl_run` |
| **KPI-5** | **1社あたり月間LLM原価** | **≤ 月額の10%** | `match_result.llm_cost_jpy` の実測（§9.5） |
| KPI-6 | 月次解約率 | ≤ 5% | Stripe |

> **KPI-1b は v3.0 で新設。** APIキーが無くてもAIの精度と無関係に測れるので、
> 設計の健全性をこれで判定する。実装済み（`evaluation/metrics.py`）。

### 2.4 やらないこと

- 応札書類の自動作成・自動提出（電子入札はICカード認証が前提。本人性・法的責任の観点から取らない）
- 入札代行・人的コンサルティング（SaaSに限定）
- 建設工事の積算・見積計算
- 全国全機関の完全網羅（§4）

## 4. スコープ

### 4.1 設計原則

**網羅性で勝負しない。「特定の業種・特定のエリアにおいては誰よりも正確」で勝負する。**

Phase 1 で全国を狙うと、機関ごとにHTML構造が違うクローラを数百本抱えることになり、
保守だけで開発リソースが枯渇する（R-1）。

### 4.2 段階設計

| Phase | 収集範囲 | 主要機能 | 次段へ進むゲート |
|-------|---------|---------|----------------|
| **W0（調査・2週間）** | — | §15 の調査。**ここを飛ばさない** | 全ての調査項目に結論が出ていること |
| **Phase 1 (MVP)** | 首都圏（1都3県＋政令市）の**役務・物品系**。目標 **30〜50機関** | 収集・正規化・ルール通知・一覧・日次ダイジェスト | KPI-1 ≤3%、KPI-1b =0%、KPI-3 ≤60分 |
| **Phase 2** | 同上 | **LLMによる仕様書読解・適合判定・要約** | KPI-2 ≥70%、**KPI-5 達成** |
| **Phase 3** | 対象エリア拡大 | 落札結果DB・過去データ分析（C-4）、LINE通知 | 継続率・ARPU |
| **Phase 4** | 全国 | 案件管理・チーム共有・API |

> **v2.0 から機関数を 50〜80 → 30〜50 に下げた。**
> 実装してみて、1サイトのクローラを「本当に壊れない状態」にするコストが想定より大きいと分かったため
> （横浜市1サイトで重大バグ2件）。§4.3 の方針で1本あたりのカバー機関数を増やして補う。

### 4.3 クローラは「機関単位」ではなく「システム種別単位」で作る（v3.0 新設）

多くの自治体は **電子入札コアシステム／入札情報公開システム（PPI）** という
共通基盤を採用しており、URL構造とDOM構造が自治体間で類似している。

→ **パーサをサイト個別に書かず、システム種別ごとに1本書いて設定で機関を差し替える。**

- 保守対象がN機関からM種別（M ≪ N）に減る。R-1・R-7（リソース枯渇）への最も効く対策。
- 1種別が壊れると複数機関が同時に壊れるため、**機関単位のヘルス監視は維持する**（§7.3）。
- ⚠️ どの自治体がどの種別かは未調査。**W0-3 で分類する**（§15）。

### 4.4 収集対象としないもの

| 対象 | 理由 |
|------|------|
| **調達ポータル（GEPS）** | **認証必須**（実測確認済み）。§0.2-A |
| ログインを要する機関サイト | 同上 |
| 官報（有償） | 費用対効果を W0 で判断 |

### 4.5 ユーザー像

| ID | 像 | Phase 1 |
|----|----|---------|
| **P-1（主）** | 従業員5〜50名の**役務・物品系**事業者（システム開発、印刷、清掃、人材派遣、機器販売）の営業兼務経営者 | **対象** |
| P-2 | 建設・設備工事事業者 | 対象外。地元1自治体の取りこぼしが即解約につながり、MVPの品質では耐えられない |
| P-3 | 入札参入を検討中の未資格事業者 | 対象外（Phase 3） |

## 5. 用語

| 用語 | 定義 |
|------|------|
| 調達機関 | 入札を発注する国・自治体・独法等 |
| 公告 | 入札の実施を公表する行為・文書。案件の起点 |
| 一般競争入札 | 参加資格を満たす者が誰でも参加できる方式 |
| 指名競争入札 | 発注者が指名した者のみ参加できる方式 |
| 随意契約 | 競争によらず特定の相手と契約する方式 |
| 企画競争／公募型プロポーザル | 価格でなく企画提案で選定する方式 |
| 全省庁統一資格 | 国の物品・役務調達に共通の競争参加資格。等級A〜Dと**営業品目**を持つ |
| 入札参加資格（指名願い） | 自治体ごとに個別申請が必要な資格 |
| **種目コード** | 発注機関が案件に付ける業種分類。**構造化されていればAI不要で絞り込める**（§9.2） |
| 電子入札コアシステム／PPI | 多くの自治体が採用する共通基盤（§4.3） |
| natural_key | 本システムが自前で作る案件の同一性判定キー |

## 6. 機能要件

### 6.1 情報収集

| ID | 要件 | 優先 |
|----|------|------|
| FR-101 | 登録された調達機関の公告ページを定期クロールし、新規・更新公告を検出する | M |
| FR-102 | クロール間隔は機関単位で設定可能（既定60分。夜間は緩和） | M |
| FR-103 | テキストPDF／HTML／Excel(.xlsx)／Word(.docx)／CSV から抽出する。**対象外形式は §7.5 に従い必ず記録する**（黙って無視しない） | M |

## 7. 品質と監視

### 7.1 「正しい結果」の具体例

1. プロフィール「業務システム開発・全省庁統一資格 役務B・首都圏」に対し、
   案件「○○市 業務システム改修業務委託（一般競争入札・予定価格非公表・締切9/20 17時）」が
   **当日中に通知される**。
2. 案件名が「令和8年度 ○○事務支援業務」で、仕様書PDFを開くと実態が「RPA導入支援」である案件について、
   **仕様書を読んだ上で**関連ありと判定し、要約に「RPAによる定型業務自動化の導入支援。期間8か月」と示す。
3. 予定価格が「非公表」の案件で、金額欄に **0円ではなく「非公表」** と表示される。
4. 予定価格が「1,234千円」の案件が、**1,234,000円**として金額レンジに乗る。
5. 締切「令和8年3月20日」（時刻記載なし）の案件が、**3月20日中は一覧に残る**。
6. 訂正公告で締切が1週間延びたとき、**別案件にならず**、締切変更が通知される。

### 7.2 「間違った結果」の具体例

1. **【最悪】** キーワードに完全一致する案件が公告されたのに、AIが「関連なし」と判断して通知されない。
2. **【最悪】** キーワードを設定していない利用者に、通知が1件も届かない。
3. 締切「令和8年3月20日 午後5時」が「2026-03-20T00:00」と解釈され、当日午前に一覧から消える。
4. 「非公表」を0円として取り込み、金額レンジ絞り込みに混入する。
5. 「1,234千円」を1,234円として取り込む。
6. AIが要約で、仕様書に書かれていない条件（「過去3年の同種実績が必要」等）を創作する。
7. サイト改修でクローラが空配列を返し続け、誰も気づかない。
8. **案件名が文字化けしたまま処理され、名寄せが破綻する**（D-1）。
9. **PDFの抽出結果が `(cid:1234)` の羅列のまま「成功」として保存される**（D-2）。
10. 同一案件が複数経路から取り込まれ、重複通知される。

### 7.3 監視（3層）

**件数の監視だけでは足りない**ことが実測で判明した（§0.5）。3層に分ける。

| 層 | 何を見るか | 検知できる故障 |
|----|-----------|--------------|
| **L1 実行監視** | `crawl_run` のステータス（ok/ok_empty/failed/partial/disabled） | 落ちた・0件になった |
| **L2 件数監視** | 直近30日平均との比率、`last_success_at` の鮮度 | 一部セレクタが壊れて件数が減った |
| **L3 データ健全性検査**（v3.0 新設） | 下表 | **L1・L2 で検知できない故障（D-1・D-2）** |

#### L3 の検査項目（FR-105 とは別立て）

| ID | 検査 | 閾値 | 検知対象 |
|----|------|------|---------|
| DQ-01 | 案件名の**文字化け率** | > 0% で異常 | D-1 |
| DQ-02 | PDF抽出テキストの **cid率**（グリフ数比） | > 20% で `unsupported_scanned` | D-2 |
| DQ-03 | 案件名の長さ分布（中央値・最小） | 前週比で急変 | パーサが別要素を拾い始めた |
| DQ-04 | 締切の**取得率**（NULL率） | 前週比で急落 | 日付カラムの位置がずれた |
| DQ-05 | 金額の取得率・**桁分布** | 桁が3つずれた分布 | 単位の解釈漏れ |
| DQ-06 | `natural_key` の**弱いキー率**（日付アンカー無し） | > 10% で警告 | 公告日が取れなくなった |
| DQ-07 | 同一機関で同一 natural_key の**衝突検出** | 1件でも異常 | 正規化が効きすぎている |

> DQ-01・DQ-02 は実装済み（`core/html.py` `looks_mojibake` / `core/attachments.py` `cid_ratio`）。
> DQ-03〜07 は Phase 1 で実装する。

### 7.4 添付ファイル対応形式（Phase 1 の線引き）

| 形式 | Phase 1 | ステータス |
|------|---------|-----------|
| テキストPDF / HTML / .xlsx / .docx / .txt / .csv | ✅ 対応 | `ok` |
| **スキャン画像PDF**（テキスト層なし・cid率超過） | ❌ 対象外 | `unsupported_scanned` |
| **一太郎(.jtd)** | ❌ 対象外 | `unsupported_format` |
| 旧形式(.xls/.doc)・ZIP | ⚠️ Phase 2 | `unsupported_format` |
| パスワード付きZIP | ❌ 対象外 | `unsupported_format` |

> **対象外は「無視」ではない。** 必ずステータスを立て、UI に
> 「未対応形式の添付があります（原本をご確認ください）」を出す。黙って落とすと §7.2-1 の取りこぼしになる。

## 8. 正規化とライフサイクルの規則

### 8.1 案件名の正規化（natural_key の前提）

**収集開始前に確定させる。後から変えると全レコード再構築になる。**

1. Unicode NFKC 正規化（全角英数字→半角、半角カナ→全角）
2. 括弧記号 `【】（）「」［］` 等を除去（**中身は残す**）
3. 年度表記（`令和8年度` `R8年度` `2026年度`）を**除去**
4. 空白を全て除去
5. 定型の接頭辞（`入札公告` `一般競争入札` `公告`）・接尾辞（`について` `の実施について`）を除去
6. 枝番（`その1` `第2回` `第2次`）は**保持する**（別案件のため）
7. 連続する区切り記号を1文字に畳む
8. **除去しきって空になった場合は除去前に戻す。真に空なら例外を送出する**（空キーは全案件を1件に潰す）

`anchor_date` は **公告日 > 入札締切日 > なし**。なしの場合は弱いキーとして DQ-06 で監視する。

### 8.2 時刻不明の締切は、用途によって逆向きに倒す（重要）

```
通知の基準時刻      → 当日 09:00  （早い側。まだ間に合ううちに知らせる）
締切超過の判定      → 当日 23:59  （遅い側。当日の案件を昼に消さない）
```

**この非対称性は意図的であり、統一してはいけない。** どちらかに揃えると必ず案件を失う。

## 9. AI要件とコスト設計（v3.0 で全面再設計）

### 9.1 AIを使う箇所と使わない箇所

| 処理 | 方式 | 理由 |
|------|------|------|
| HTMLの抽出 | ルールベース | 決定的でなければ再現性・監査可能性がない |
| 日付・金額の正規化 | ルールベース＋正規表現 | AIの誤読が致命傷になる |
| **種目コードによる絞り込み** | **ルールベース** | **発注機関が構造化して出しているなら、AIを使う理由がない**（§9.2） |
| 関連度判定 | **LLM** | 案件名だけでは判定できず、仕様書の読解が要る（C-5・§0.3） |
| 仕様書要約 | **LLM** | 同上 |

> **原則：数値・日付・分類コードにAIを使わない。文章の意味理解にだけAIを使う。**

### 9.2 コスト制御の再設計（前提Bの撤回を受けて）

v2.0 の「1段目ルール(→5%) → 2段目埋め込み(→1%) → 3段目LLM」は、
**2段目が機能しないことが実測で判明した**ため成立しない（§0.3）。

v3.0 では、**安価な事前フィルタに頼るのをやめ、コスト制御を2つの軸に移す。**

```
軸1  絞り込みを「意味理解」ではなく「構造化メタデータ」で行う
     種目コード・エリア・金額・資格等級・NG語 → ルールで決定的に落とす
     ここは無料で、かつ正確。AIより信頼できる。

軸2  LLMを2段構えにして、単価の高いモデルを使う件数を絞る
     3a 一次判定：安価モデル（Haiku級）に 案件名＋仕様書冒頭 を渡し、関連度だけを返させる
     3b 精読・要約：3a で高スコアだった案件だけ、上位モデル（Sonnet級）で要約する
```

| 段 | 手段 | 入力 | 想定通過率 | コスト |
|----|------|------|-----------|--------|
| 1 | **メタデータのルール判定**（種目コード・エリア・金額・資格・NG語） | 構造化フィールドのみ | 100% → **⚠️要実測** | 0 |
| 3a | 安価モデルで一次適合判定 | 案件名＋仕様書冒頭 **2,000字まで** | 1段目通過分の全件 | 小 |
| 3b | 上位モデルで精読・要約 | 案件名＋仕様書 **12,000字まで** | 3a で60点以上 | ここが主コスト |

> **2段目（案件名の類似度）は「通過可否の判定」から外し、
> 「表示順・優先度の並び替え」に降格する。**
> §0.3 の実測では順位付けとしては妥当に働いていたため、用途を限定して残す。
> 埋め込みを使うかバイグラムを使うかは W0-5 の再検証で決める（現状は差が無い）。

### 9.3 予算ガードレール（実装済み）

- **月間LLM実行上限**（1社あたり）。上限到達で **LLM判定は止めるが通知は止めない**（FR-305）。
- **永続キャッシュ**（TTLなし・内容ハッシュ）。仕様書の中身は変わらないので、
  再公告のたびに同じPDFへ課金しない。キャッシュヒットは予算を消費しない。
- `match_result` に **入出力トークン数と円換算コストを毎回記録**。予算管理は推測でなく実測で回す。
- 仕様書は段ごとに文字数上限で打ち切る（長大PDFで青天井に課金しない）。

### 9.4 AIの前提条件

- **AI判定は監査可能であること**：入力（案件テキスト＋プロフィール）と出力（スコア・理由）を保存し、
  後から再現・検証できるようにする。
- プロンプトに **「仕様書に書かれていないことを書いてはならない。不明な項目は『記載なし』とせよ」** を明示する（§7.2-6）。

### 9.5 KPI-5（単位経済）のゲート — Phase 2 の可否を決める

```
1社あたり月間LLM原価 = (3a単価 × 3a件数) + (3b単価 × 3b件数) − キャッシュ削減分
                     ≤ プラン月額 × 10%
```

Light プラン 9,800円 の場合、**上限 980円/月/社**。

- 3a・3b の単価と件数は **W0-4 で実測する**（§15）。
- **この式を満たせない場合、Phase 2 に進んではならない。**
  取りうる手は ①1段目のメタデータ絞り込みを強化する ②3b の対象を減らす
  ③価格を上げる ④仕様書読解を上位プラン限定にする。
- ⚠️ v3.0 時点で単価は**未実測**。`ANTHROPIC_API_KEY` が必要（§15 W0-4）。

## 10. 評価セットと計測（v3.0 で厳格化）

### 10.1 作成の原則

| # | 規則 | 理由 |
|---|------|------|
| 1 | **実装者は評価セットを作らない。** QA（天城）が作る | 作った本人が採点すると測定にならない |
| 2 | **dev / test を分離する。** dev 100件は開発中に見てよい。**test 200件は最終計測時まで開けない** | 検証で「合成30件に合わせて閾値を調整する」誘惑が実際に発生した。テストセットに触れると測定器が壊れる |
| 3 | 対象機関から**無作為抽出**した実案件を使う。合成データで代替しない | 合成データは自分の想定しか含まない |
| 4 | **2名が独立にラベル付けし、Cohen's κ ≥ 0.7** を満たすこと。下回ればラベル基準を見直す | 「関係あるか」の基準が曖昧なら、そもそも測定できない |
| 5 | **各案件に仕様書本文を含める** | 仕様書が無い状態で測ると3段目を評価できない（実際にこの欠陥で26.7%という誤った数字を出した） |
| 6 | 四半期ごとに更新し、FR-308 のフィードバックを候補に回す | 案件の傾向は変わる |

### 10.2 計測する指標

| 指標 | 意味 | 目標 |
|------|------|------|
| **KPI-1b 構造的取りこぼし率** | 関係ある案件のうち、判断の機会を得られなかった割合 | **0%** |
| KPI-1 取りこぼし率 | 関係あるのに通知しなかった割合 | ≤ 3% |
| KPI-2 適合率 | 通知したうち実際に関係があった割合 | ≥ 70% |
| 正規化精度（日付・金額） | 数値項目はAIを使わないので、外れたら実装バグ | ≥ 99.5% |
| 要約のハルシネーション率 | 仕様書に無い固有名詞・条件が出たら不合格 | **0%** |

> **KPI-1b を先に達成すること。** 構造的に届いていない案件は、
> AIをどれだけ良くしても拾えない。順序を逆にすると、AIのチューニングで
> 解決しない問題をAIのチューニングで解こうとして時間を溶かす。

## 12. アーキテクチャ

### 12.1 スタック（確定）

| 層 | 技術 | 根拠 |
|----|------|------|
| クロール／解析／マッチング | **Python 3.11+**（`requests` `bs4` `lxml` `pdfplumber` `openpyxl` `python-docx` `playwright`） | 検証で全て動作確認済み。社内の既存プロダクトと同一言語で、DAL・セキュリティ層・Adapterパターンを流用できる |
| DB | **Supabase / PostgreSQL**（RLS必須）。検証は SQLite で同一スキーマ | 全社共通基盤 |
| フロント | Next.js（App Router） | 全社共通基盤 |
| 課金 | Stripe | 全社共通基盤 |
| **ジョブ実行基盤** | **Vercel の外**（VPS / Cloud Run 等） | §12.2 |

### 12.2 「Vercelに全部載せる」前提は最初に捨てる

| 制約 | 内容 |
|------|------|
| 実行時間 | 数十機関のクロールは1回の Function 実行に収まらない |
| ヘッドレスブラウザ | ASP.NET／JS依存サイト用。Vercel 上では実質動かせない |
| 定期実行 | 社内の既存プロダクトは全てリクエスト駆動で、日次ジョブの前例が無い |

→ **クロール層は分離した実行基盤に置く。** Web/API 層のみ Vercel。
ここを曖昧にしたまま進めると後半で全部作り直しになる。

### 12.3 クローラの2系統分離（FR-112）

| 地雷 | 所属 |
|------|------|
| ASP.NET WebForms（`__VIEWSTATE` を保持したPOSTが必須） | HTTP群（セッション保持あり） |
| 検索必須型（一覧ページが無く、条件を入れないと何も出ない） | HTTP群 or ブラウザ群。**網羅性が構造的に保証できないため検索条件の総当たり設計が要る** |
| JS依存 | **ブラウザ群**（逐次実行。1件あたりの時間とメモリが10倍） |
| セッションタイムアウト | 両群（セッション再取得を実装） |
| 和暦・全角数字 | 正規化層（§8.1・FR-203） |
| **charset を返さないサーバ** | **HTTP層。`response.text` を使わず bytes を渡す規約**（D-1） |

## 13. 法務・コンプライアンス

> 本節は一般的な整理であり、**本番公開前に弁護士のレビューを受ける**（§3-7）。

| ID | 要件 | 優先 |
|----|------|------|
| CR-101 | クロール対象ごとに**利用規約・robots.txt を事前確認して記録**してから収集を開始する。未確認の機関は収集しない | **M** |
| CR-102 | 1サイトあたり同時接続1・間隔1秒以上を下限とする。User-Agent に**サービス名と問い合わせ先**を明記 | **M** |
| CR-103 | 公告本文の**全文転載を既定としない**。要約とスニペットに留め、原文リンクへ誘導 | **M** |
| CR-104 | 担当者名・連絡先が含まれる場合はマスクする | S |
| CR-105 | 応札判断支援は**公表済み実績の可視化に限定**し、価格の示唆・入札行動の誘導を行う表現を禁止する（独占禁止法） | **M** |
| CR-106 | 「情報の正確性・網羅性を保証しない。最終確認は発注機関の原文で」を規約とUIに常時明示 | **M** |
| CR-107 | 削除・掲載停止の申し出に対応する窓口を設置 | S |
| CR-108 | **サービス名の商標調査（J-PlatPat）とドメイン確保を、開発着手前に完了する** | **M** |

**追い風となる根拠**：著作権法13条（国・地方公共団体の告示等は著作権の目的とならない）、
30条の4（情報解析）、47条の5（所在検索・情報解析サービスの軽微利用）、
政府標準利用規約（第2.0版）。
ただしこれらは**著作権の問題が小さいことを示すに過ぎず**、
サイト利用規約による契約上の制限とアクセス負荷のリスクは別問題。CR-101・CR-102 が実質的な防御線。
